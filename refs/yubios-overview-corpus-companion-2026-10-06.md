# yubios overview corpus companion (2026-10-06)

The refs-side mirror of the `yubi-OS/knowledge` corpus `knowledge/yubios/`, a 6-doc knowledge space about yubiOS itself: what it is, what it trusts, and how it proves it. This doc distills the corpus for refs/ readers and points back to the corpus for the full cited versions. Every claim here is grounded in the corpus text; nothing new is asserted beyond it.

## What the corpus covers

- `knowledge/yubios/01-architecture-overview.md`: immutable image-mode Linux. The OCI image is the unit of delivery, bootc and mkosi are two build paths sharing one `usr/` overlay with byte-identical kernel cmdlines, composefs plus dm-verity make `/usr` verified on read, systemd-repart creates and encrypts all partitions on first boot so the LUKS2 root key never exists off-device, and systemd-sysupdate gives A/B atomic upgrades with Boot Assessment rollback.
- `knowledge/yubios/02-yubikey-trust-boundaries.md`: YubiKey as sole root of trust at 5 boundaries: PIV slot 9c via CCID for Secure Boot UKI signing (FIDO2 rejected there, ADR-002), LUKS2 unlock via FIDO2 hmac-secret with no TPM slot (ADR-003), `ed25519-sk` resident SSH keys (ADR-004), pam-u2f required-mode login and sudo (ADR-005, pinned 1.3.1+ for CVE-2025-23013), and per-user systemd-homed LUKS2 volumes (ADR-009). Thesis: "No TPM. No OEM. No trust anchors you don't control."
- `knowledge/yubios/03-boot-chain-and-ukis.md`: the boot chain link by link. UKI signed via systemd-sbsign with a PIV 9c PKCS#11 key (SoftHSM in CI), the dm-verity roothash embedded in the signed UKI command line, composefs as a separate integrity model on the bootc path with kernel floors 6.5 / 6.6 / 6.12, and the sealed-UKI QEMU Secure Boot VM lane (OMN-53) with its 6 positive and 3 negative assertions. Carries an in-doc drift flag: `mkosi.conf` carries no `Verity=` key despite ADR-007 and skill claims.
- `knowledge/yubios/04-supply-chain-gates.md`: 4 layered gates. Digest pinning of every build input (ADR-015, ADR-030), a default-deny OPA/Rego Buildx build policy (`yubiOS.rego`) vetting every `FROM` before any layer executes, two-build no-cache byte comparison as proof of reproducibility, and cosign signatures plus SLSA v1.0 provenance and SPDX SBOM attestations with a Build L3 target and Rekor v2 posture (OMN-157 spec).
- `knowledge/yubios/05-arm64-hardware-path.md`: ADR-023 makes ARM64 primary. RK3588 Path A on Radxa ROCK 5B (owner-burned ROTPK, TF-A Trusted Board Boot), ROCKPro64 (RK3399) as secondary, QEMU virt as CI firmware baseline. TF-A / OP-TEE / U-Boot / ms-tpm-20-ref fTPM as an OP-TEE Early TA with the RPMB-before-tee-supplicant bootstrap hazard. Blocker B-RK3588-TPL: the DDR/TPL blob makes the published ROCK 5B bundle diagnostic, not flashable. OMN-36, the v1 launch gate, has slipped 3 consecutive times.
- `knowledge/yubios/06-ci-and-test-infrastructure.md`: CI exists to prove the image boots. `ci.yml` is a dumb group-routing dispatcher over 39 workflow files, 2 self-hosted ARM64 runners (rock1, and ubuntu HIGH-MEM), 3 bcvk VM lanes (`ci_test-vm`, `ci_test-vgpu-vm`, `ci_test_sealed-uki-vm`, the last green at V83), a shared reproducible-build library, and `playbooks/` runbooks whose rule 4 is "never fabricate: unqueried means say I have not verified this yet."

## Key takeaways

1. One root of trust, held by the owner. Every boundary that matters anchors to a YubiKey the user physically holds and generates keys on. Where a TPM exists (the ARM64 fTPM), it adds platform-integrity attestation and never becomes the disk-unlock gate; ADR-011's rationale is that FIDO2 hmac-secret survives kernel and boot-config changes without re-enrollment, while PCR-hash policies break on every update.
2. Verification replaces trust. Digest-pinned inputs, a default-deny build policy, SLSA provenance, and owner-held UKI signing mean a poisoned contribution fails verification instead of shipping. Immutability is the enforcement mechanism: `SignExpectedPcr=no` plus roothash-in-UKI means tampering is detected before any userspace runs.
3. Sealing is proven in layers, and the corpus is honest about which layer is missing. The sealed-UKI lane proves the primitive (signed UKI, ROTPK, dm-verity, sealed LUKS2 in a QEMU Secure Boot VM); the bootc composefs install is still strict fs-verity plus an unsealed BLS entry until OMN-150 Phase 2 wiring lands. On ARM64, both boards stay Path B for production claims until the 9-item promotion checklist has evidence.
4. Drift is documented, not hidden. The corpus records 4 version-sensitive findings from the redo itself: the missing `Verity=` key (doc 03), the Rekor v2 GA dating conflict (doc 04), unrecorded TF-A/OP-TEE board-lane pins (doc 05), and the `ci.yml` header comment plus CI_MAP lagging the code's group dispatch so `group=all` silently misses 3 workflows (doc 06).
