# yubiOS Threat Model

Status: repository-scoped planning baseline for `main`

This threat model is derived primarily from [ARCHITECTURE.md](ARCHITECTURE.md) and [MITIGATE.md](MITIGATE.md), with normative invariants cross-checked against [SPEC.md](SPEC.md) and supply-chain pinning rules cross-checked against [PINNED.md](../PINNED.md). It models the intended system and explicitly distinguishes documented controls from controls that still need hardware or implementation validation. It is not evidence that every control is implemented correctly.

## Overview

yubiOS is a FIDO2-first immutable Linux operating system delivered through bootc/OCI and mkosi image paths. Its owner-facing root of trust is an owner-held YubiKey 5: PIV slot 9c signs Secure Boot artifacts, FIDO2 `hmac-secret` gates disk and home unlock, FIDO2 resident credentials protect SSH, and pam-u2f protects login and `sudo`. TPM/fTPM measurement is deliberately separate from owner identity and must not become the sole disk-unlock gate.

The primary platform is ARM64. The intended production Path A uses owner-provisioned ROTPK state, TF-A Trusted Board Boot, OP-TEE, an RPMB-backed fTPM and UEFI variable service, U-Boot UEFI, systemd-boot, and a signed unified kernel image (UKI). ARM64 Path B uses verified or measured boot where an owner-enforced hardware root cannot safely be provisioned; it is not equivalent to Path A. x86-64 is supported above the UKI, but OEM firmware and the platform TPM remain unavoidable lower-layer trust anchors.

The runtime design separates immutable verified operating-system content from encrypted writable state. `/usr` is intended to be read-only and verified through composefs/erofs and dm-verity. Root state, swap, and per-user homes are LUKS2-encrypted and unlocked with FIDO2 plus separately managed recovery material. Updates use A/B `/usr` slots, signed UKIs, boot-attempt counters, and a health check that marks a new boot good.

The repository also contains a security-critical software-supply-chain surface: pinned upstream images and GitHub Actions, build policy in `yubiOS.rego`, bootc and mkosi builds, firmware bundles, CI tests, provenance and SBOM generation, and publication to an OCI registry. A release is only as trustworthy as both the owner-controlled boot-signing boundary and the build/publish path that selected the bytes to be signed.

### Assets and security objectives

| Asset or objective | Required property | Consequence if lost |
|---|---|---|
| YubiKey PIV private key and enrolled Secure Boot certificate | Non-exportability, authorized use, correct enrollment, and protected signing ceremony | Attacker-controlled boot artifacts may be accepted as owner-authorized |
| FIDO2 credentials, PINs, and recovery keys | Confidentiality, phishing-resistant use, revocability, and recoverability | Disk, home, SSH, or privileged-session compromise; or permanent owner lockout |
| Root, swap, and user-home plaintext | Confidentiality while powered off; least exposure while unlocked | Disclosure of credentials, personal data, build secrets, and administrative material |
| Boot chain and immutable `/usr` | Authenticity, integrity, anti-rollback policy, and fail-closed verification | Persistent pre-login compromise or subversion of every higher-layer control |
| ARM64 ROTPK, RPMB state, fTPM NV, and UEFI variables | Correct provisioning, integrity, freshness, and device binding | False measurement, key substitution, rollback, or a broken owner-controlled platform root |
| OCI, UKI, disk-image, and firmware release artifacts | Reproducible provenance, approved inputs, platform separation, and authentic publication | Fleet-wide or cross-install supply-chain compromise |
| CI credentials, registry credentials, and repository controls | Least privilege, branch integrity, auditability, and resistance to untrusted contributions | Unauthorized builds, tags, attestations, or releases |
| Update and recovery path | Atomicity, rollback safety, authenticity, and availability | Persistent malicious update, downgrade, boot loop, or unrecoverable device |
| Administrative identities and active sessions | Correct PAM/SSH authorization, physical presence, and session isolation | Local or remote privilege escalation despite possession-based controls |

### Security invariants

The following invariants are the center of the model. A vulnerability that violates one should be evaluated at the boundary it defeats, not merely at the file where it appears.

1. Mandatory owner key material is generated by or for the owner, remains owner-controlled, and gates owner actions.
2. Every boot component is authenticated, measured, or hash-verified before its authority is relied upon; measured-only Path B must never be represented as enforce-before-execution Path A.
3. The signed UKI binds the kernel, initrd, command line, and dm-verity root needed to authenticate `/usr`.
4. Writable state cannot silently replace verified `/usr` content or redirect boot into unverified content.
5. Disk and home unlock require the intended FIDO2 credential, PIN, and physical presence, with recovery material kept as an explicit and separately protected bypass path.
6. TPM/fTPM evidence complements YubiKey possession; it never silently replaces the owner-held gate for disk unlock.
7. Production builds accept only approved digest-pinned inputs, and TEST-only authenticators or development artifacts cannot be promoted under production tags.
8. A/B update rollback and boot-health logic cannot make an unauthenticated artifact authoritative or mark a compromised boot healthy merely because it reached userspace.
9. Privileged exceptions, especially raw hardware access during first-boot firmware inspection and enrollment, remain narrow, one-shot, and unable to become a general persistence path.
10. Loss or failure of one authentication mechanism does not force the owner into an undocumented or weaker recovery path.

## Threat Model, Trust Boundaries, and Assumptions

### Actors and attacker capabilities

| Actor | Control and trust level |
|---|---|
| Owner/operator | Controls the YubiKey, recovery key, Secure Boot enrollment, installation target, and upgrade decisions. Trusted to intend the selected action, but mistakes, coercion, token theft, and unsafe recovery handling remain realistic. |
| Repository maintainer/release engineer | Controls source, pinned inputs, CI policy, and release configuration. Privileged but fallible; account or workflow compromise is in scope. |
| CI runner and publication infrastructure | Processes source and secrets and emits images, firmware, attestations, and tags. It is a high-value trust boundary rather than an inherently trusted oracle. |
| Upstream project or image publisher | Supplies base images, actions, compilers, firmware components, and packages. Content may be vulnerable or malicious even when digest-pinned. |
| Network or registry attacker | Can intercept, delay, replay, mirror, or substitute downloads and registry responses, but is not assumed to break modern cryptography. |
| Local unprivileged attacker | Controls user files, application inputs, removable media, IPC, and possibly a logged-in process; seeks privilege escalation or cross-user access. |
| Physical attacker | May steal a powered-off device or obtain temporary access to the platform, ports, storage, firmware setup, or peripherals. A strong physical attacker may also steal the YubiKey, but may not know its PIN. |
| Supply-chain or firmware attacker | May compromise an upstream input, CI workflow, signer-adjacent host, OEM firmware, board provisioning process, or pre-owner hardware stage. |
| Post-unlock attacker | Has code execution after the owner has unlocked the system. Mounted plaintext and the active session are exposed; immutable boot content still matters for persistence and recovery. |

### Trust boundaries

| Boundary | Data or authority crossing it | Expected control | Important residual risk |
|---|---|---|---|
| Owner ↔ YubiKey | PIN entry, touch, PIV signing, FIDO2 assertions and `hmac-secret` | Separate CCID/PIV and hidraw/FIDO2 interfaces; PIN and physical presence for sensitive actions | A compromised but correctly signed host can request a valid FIDO2 secret; possession does not attest to the requesting OS |
| YubiKey ↔ host USB stack | Authentication and secret-release protocol messages | Hardware-backed non-exportable credentials and verification-required policies | Malicious USB stack, counterfeit token, confused interface selection, or unsafe enrollment ceremony |
| Hardware/firmware ↔ first owner-controlled boot stage | ROTPK, firmware images, Secure Boot variables, TPM measurements | ARM64 Path A TBB and owner provisioning; owner-enrolled UEFI keys above OEM firmware on x86-64 | Closed ROM/SoC and x86 OEM firmware remain below the enforceable boundary; Path B is measured rather than equivalent to fused verification |
| Boot chain ↔ runtime | UKI, command line, PCRs, dm-verity root, initrd policy | Signed UKI, PCR 11 measurements, `usrhash=`, dm-verity, kernel lockdown | A compromised verifier or firmware can lie about every higher layer; writable early-boot inputs must not redirect trust |
| Immutable `/usr` ↔ writable root and user state | Configuration, service state, caches, logs, secrets, and user content | Read-only verified `/usr`, encrypted writable partitions, systemd sandboxing | Runtime root can alter writable state, steal plaintext, or create persistence outside `/usr` unless every boot-relevant writable input is constrained |
| Build source ↔ CI runner | Pull-request content, workflow definitions, build scripts, pins, secrets | Pinned Actions/images, policy gates, review controls, isolated CI contexts | Workflow injection, compromised maintainer accounts, overly broad tokens, and malicious-but-pinned upstream content |
| CI/release system ↔ registry | OCI indexes, per-commit tags, firmware tags, SBOMs, provenance | Digest-addressable artifacts, authenticated publication, attestations | Provenance records origin but does not by itself make malicious output safe; mutable convenience tags can be replayed or retargeted |
| Registry/update source ↔ installed system | Candidate OS image, UKI, `/usr` partitions, update metadata | TLS, signed boot artifacts, dm-verity, immutable commit tags, A/B boot counting | Selection, downgrade, and rollback policy can fail even when each selected artifact is internally valid |
| New update ↔ boot-good state | Health signal and boot-attempt counter | systemd-boot counters, fallback slot, `bootctl set-boot-good` after health checks | A malicious signed userspace may forge health; availability rollback is not authenticity validation |
| First-boot tools ↔ raw platform state | Disk partitioning, key enrollment, firmware inspection, UEFI variables | `ConditionFirstBoot=yes`, measured-boot gate, narrow service privileges | This is a one-time concentration of authority; target confusion or a weak measured-boot predicate can permanently enroll attacker choices |

### Input classification

Attacker-controlled inputs include network and registry responses; OCI metadata and layers until authenticated by policy; removable media and USB devices; on-disk partition tables, filesystems, ESP contents, and writable state after physical access; untrusted application data; packets to any enabled service; user-controlled files processed by privileged tools; and pull-request content executed by CI. Firmware tables, device trees, TPM event logs, and UEFI variables must also be treated as untrusted evidence whenever they originate below an unowned firmware boundary.

Operator-controlled inputs include the target disk, Secure Boot key enrollment, YubiKey and recovery credential enrollment, PIN/touch decisions, board Path A/Path B classification, fuse-burning procedure, fail-open versus fail-closed firmware checks, selected release or upgrade, and emergency recovery actions. These inputs are authorized but not automatically safe.

Developer-controlled inputs include source and configuration, `Containerfile` variants, mkosi profiles, `yubiOS.rego`, systemd units and scripts under `usr/lib/`, workflow YAML, dependency pins, firmware component revisions, test images, release tags, health criteria, and documentation that determines operator behavior. A compromised developer identity turns these into attacker-controlled inputs.

### Assumptions and exclusions

- Standard cryptographic primitives, YubiKey hardware isolation, PIV/FIDO2 implementations, LUKS2, Secure Boot verification, and dm-verity are assumed sound unless yubiOS configures or composes them unsafely.
- The owner protects PINs and offline recovery material, verifies enrollment prompts, and does not intentionally enroll attacker-controlled keys. Coercion and a malicious owner are outside the prevention goals.
- ARM64 Path A is not production-established until real boards demonstrate safe ROTPK/fuse provisioning, RPMB-backed state, debug lockdown, and the documented chain. QEMU and Path B evidence cannot substitute for that proof.
- x86-64 cannot claim an owner-controlled root below the UKI while OEM UEFI and the OEM TPM remain trusted.
- A malicious CPU/SoC, immutable closed ROM behavior, and hardware implants below the selected platform boundary are out of scope. Their presence must not be obscured by higher-layer attestation claims.
- Application-level vulnerabilities are outside the product specification, but an application remains an attacker entry point into the active user session. OS sandbox escapes, cross-user compromise, and persistence into trusted system state remain in scope.
- A powered-on, unlocked system exposes mounted plaintext to sufficiently privileged malware. The goal after unlock is containment, least privilege, and preventing durable subversion of the trusted boot path—not retroactive confidentiality from root.
- VM, SoftHSM, and software-FIDO2 tests establish functional behavior only. They do not prove token hardware properties, physical-presence semantics, firmware ownership, RPMB freshness, fuse state, or real-board debug lockdown.

## Attack Surface, Mitigations, and Attacker Stories

### Control maturity

| Maturity | Controls in this model |
|---|---|
| Architectural or normative requirement | Owner-controlled signing, FIDO2 unlock, signed UKI, verified `/usr`, no TPM-only unlock, digest-pinned build inputs, production/dev separation, narrow privileged services |
| Environment-dependent control | Secure Boot variable enforcement, TPM/fTPM measurement, `ConditionSecurity=measured-os`, kernel lockdown, BPF-LSM-backed filesystem restrictions, systemd service sandboxing, registry TLS/PQ negotiation |
| Needs real-hardware or end-to-end validation | ARM64 Path A fuse state, TF-A/OP-TEE/U-Boot chain, RPMB-backed fTPM and UEFI NV, CoreSight/debug lockdown, recovery from interrupted provisioning, physical YubiKey ceremonies |
| Proposed or detection-only | U-Boot FIDO2 console gate; CHIPSEC warning-mode inspection; automated Absolute/Computrace conclusions that MITIGATE.md says cannot currently be reliable |

Controls in the last two rows must not reduce severity as if they were proven preventive controls.

### Principal attacker stories

| Surface | Attacker story and impact | Existing controls | Residual risk and review focus |
|---|---|---|---|
| Source and dependency supply chain | A compromised maintainer, Action, base image, package source, or firmware fork injects code that is built and published as yubiOS. | Approved SHAs and image digests in `PINNED.md`; strict `yubiOS.rego` policy; immutable commit tags; provenance and SBOM generation. | A digest pins identity, not trustworthiness or freshness. Review workflow token scope, untrusted-PR execution, pin-update authorization, builder isolation, provenance verification, and whether one identity can both change policy and publish. |
| Signing and release | An attacker controls the host that invokes the YubiKey PIV key, tricks the owner into authorizing a malicious UKI, or substitutes the enrollment certificate. | Non-exportable PIV key in slot 9c, owner-enrolled Secure Boot db, `systemd-sbsign`, and `sbverify` checks. | Non-exportability does not prevent unauthorized signing through a compromised host. Verify PIV PIN/touch policy, ceremony display/confirmation, certificate replacement controls, revocation, and separation between build approval and signing. |
| Registry and update selection | A network or registry attacker serves an old, wrong-platform, development, or malicious image and attempts to make it boot. | TLS, digest-addressable references, production/test tag separation, signed UKI, dm-verity, provenance/SBOM, and A/B fallback. | Mutable `latest` is a selection risk; signing authenticates an artifact but may not enforce freshness or channel. Verify signed update metadata, anti-rollback version state, architecture binding, provenance policy, and that `dev`/swu2f content can never reach production tags. |
| ARM64 platform provisioning | A malicious board, provisioning tool, or operator error burns the wrong ROTPK, leaves debug enabled, uses volatile rather than RPMB-backed NV, or labels Path B as Path A. | Explicit Path A/Path B classification, owner-burned ROTPK design, TBB, OP-TEE, fTPM, StandaloneMM, sacrificial-board rehearsal. | Fuse changes may be irreversible and current real-board proof is incomplete. Provisioning must verify before burning, read back state, bind artifacts to the board, lock debug paths, and provide a tested recovery/abort procedure. |
| x86-64 or Path B firmware | Compromised OEM firmware or a measured-but-not-enforced stage lies about measurements, tampers with input, or loads a valid but attacker-selected UKI. | Owner-enrolled Secure Boot above firmware, PCR measurements where available, signed UKI, and explicit documentation of the weaker boundary. | Measurement is not prevention. Findings below the unowned boundary may be out of remediation scope but remain decisive limitations; yubiOS must not overstate attestation confidence. |
| Evil-maid boot and FIDO2 secret release | A physical attacker changes firmware, boot UI, or early userspace so the next owner PIN/touch releases a valid FIDO2 `hmac-secret` to attacker-controlled code. | Secure Boot, signed UKI, dm-verity, owner-controlled ARM64 chain where available, FIDO2 PIN and touch. | FIDO2 proves possession and interaction, not the requesting OS identity. The attack is blocked only to the extent the complete pre-unlock chain is enforced. Trusted UI and recovery prompts are important review targets. |
| Powered-off storage theft | An attacker steals or images the disk and attacks root, swap, or homes offline. | LUKS2, FIDO2 `hmac-secret`, client PIN, touch, per-user homed encryption, and offline recovery key. | Recovery-key entropy/storage and LUKS parameters are equally important. Theft of both token and PIN, implementation flaws, or weak recovery handling defeats the intended protection. |
| Active-session compromise | A malicious app, remote service exploit, or local privilege escalation runs after unlock and reads mounted data or asks the token to perform authorized operations. | Per-user homes, SSH verification-required guidance, required pam-u2f flow, systemd sandboxing, immutable `/usr`, and kernel lockdown. | Encryption no longer protects mounted plaintext. Review token-presence caching, agent forwarding, socket and device ACLs, hidraw/CCID access, secret logging, and barriers between an unprivileged session and privileged token operations. |
| Writable-state persistence | Runtime root or a physical attacker alters `/etc`, `/var`, boot state, generators, credentials, or other writable inputs while `/usr` remains valid. | Verified read-only `/usr`, signed UKI command line, encrypted root state, DPS discovery, sandboxed services. | dm-verity protects only covered bytes. Inventory every writable input consumed before or during privileged startup and ensure it cannot replace binaries, weaken PAM, redirect mounts, inject kernel arguments, or mark an update good. |
| First boot and enrollment | An attacker exploits disk parsing, USB handling, firmware inspection, target selection, or a privileged script during the one-time setup window and enrolls attacker-controlled state. | `ConditionFirstBoot=yes`, measured-OS expectation, one-shot services, scoped raw hardware access, re-runnable enrollment steps. | First boot combines maximum privilege with untrusted hardware and operator input. Verify fail-closed preconditions, idempotence, atomic writes, safe target identification, secret-free logs, rollback, and behavior when the YubiKey is removed mid-step. |
| TPM/fTPM and attestation | A compromised secure world, replayed NV state, incorrect PCR policy, or forged event interpretation makes a bad boot look acceptable. | Owner-owned ARM64 fTPM design, RPMB-backed production state, PCR 11 boot-phase measurement, measured-OS conditions, and YubiKey kept as the unlock gate. | TPM evidence is only as trustworthy as firmware, NV freshness, event replay, and verifier policy. Volatile CI NV and OEM TPMs must not be treated as production-equivalent. |
| Authentication and recovery | A PAM ordering error, version regression, emergency shell, SSH option, or recovery flow bypasses PIN/touch or grants privilege after token loss. | pam-u2f 1.3.1+, `required` PAM entries, resident `ed25519-sk` keys, PIN verification guidance, and separate recovery material. | Test every applicable PAM stack and failure mode, including absent token, wrong PIN, locked token, offline boot, recovery boot, and package upgrade. Recovery must restore availability without becoming the easiest authentication path. |
| Update health and rollback | A faulty or malicious update boots far enough to mark itself good, corrupts both slots, or forces a downgrade to a known-vulnerable but valid image. | Separate A/B `/usr` slots, three-attempt boot counter, health validation, and `bootctl set-boot-good`. | Health checks are availability controls, not proof of integrity. Protect the boot-good signal, preserve a known-good slot, authenticate all update metadata, and define minimum acceptable versions. |
| Firmware inspection service | An attacker abuses CHIPSEC's raw hardware access or treats warning-only output as a security verdict. | One-shot service, first-boot and measured-OS gates, explicitly scoped raw access, optional fail-closed fleet policy. | A parser or command-injection flaw here has unusually high impact. CHIPSEC cannot reliably prove absence of Absolute/Computrace; informational evidence must not be presented as a clean bill of health. |
| Extensions, portable services, containers, and apps | A less-trusted extension or application escapes isolation or introduces mutable code into a trusted namespace. | Verity/PKCS#7 for sysext and portable-service images, isolated roots and namespaces, weaker trust explicitly assigned to Flatpak/OCI apps. | Enforce signature policy and namespace/capability boundaries. Treat end-user apps as hostile to the active user and ensure they cannot access raw YubiKey interfaces or host update/signing authority by default. |
| Availability and denial of service | An attacker or accident locks the YubiKey, exhausts boot attempts, corrupts writable state, fills partitions, interrupts fuse/enrollment operations, or removes access to registry artifacts. | Offline recovery key, re-runnable enrollment, A/B fallback, immutable images, and explicit Path A rehearsal. | Recovery procedures are security-critical code and documentation. A recoverable denial of service is lower severity than key disclosure, but irreversible fuse mistakes, both-slot corruption, or fleet-wide update lockout can be high impact. |

### Vulnerability classes that matter most

The highest-value review classes are boot-chain verification bypasses; artifact-signing or update authorization bypasses; rollback and cross-channel substitution; CI workflow injection and secret exposure; unsafe handling of untrusted partitions, filesystems, firmware tables, device trees, USB devices, and OCI metadata in privileged code; local privilege escalation and systemd sandbox escape; PAM/SSH/FIDO2 miscomposition; recovery-path bypass; writable-state persistence around dm-verity; TPM/fTPM freshness or attestation confusion; and production leakage of TEST-only authenticators.

Traditional web classes such as CSRF, browser XSS, SQL injection, and multi-tenant object authorization are low relevance unless a corresponding web control plane is introduced. Application vulnerabilities with no route across the user, privilege, or immutable-system boundary are outside the core product model. Issues that require an already malicious CPU/SoC, deliberate owner enrollment of attacker keys, or control of closed ROM below the declared boundary are generally limitations rather than actionable yubiOS vulnerabilities, unless repository code falsely claims to detect or prevent them.

## Severity Calibration (Critical, High, Medium, Low)

Severity is based on the strongest realistic deployment described by the repository while accounting for maturity. Raise severity when an issue is remotely triggerable, affects default production images, crosses from untrusted input into release or pre-boot authority, persists below or around the signed UKI, affects both architectures or an entire release channel, or defeats independent controls such as both artifact authenticity and YubiKey presence. Lower severity when the path is TEST-only, Path B-only and accurately labeled, requires prior root or malicious firmware already outside the boundary, depends on deliberate owner misconfiguration, or only weakens non-authoritative telemetry.

### Critical

- A repository/CI/release flaw lets an untrusted contributor publish an attacker-controlled production image or firmware bundle that passes the normal trust and signing path for many installations, without a second trusted approval.
- A verification or key-management flaw remotely or persistently defeats the owner-controlled boot chain and enables pre-unlock code to capture owner data or authorize arbitrary future boots across affected devices.
- A production/dev separation failure ships a known TEST authenticator or universal bypass in the production channel and permits disk unlock or administrative authentication without the owner's credential.

Critical generally requires broad, durable compromise of the platform or release root of trust. A bug confined to an explicitly non-production VM or unprovisioned Path B board is not critical merely because similar code may later be used in Path A.

### High

- A local physical attacker can bypass enforced Secure Boot or FIDO2-gated LUKS and recover protected data from a powered-off production device without the token, PIN, or recovery key.
- A malicious registry response can select a vulnerable or attacker-controlled but otherwise well-formed update because production lacks effective authenticity, channel, architecture, or anti-rollback enforcement.
- An unprivileged process in a normal active session can reach root, cross into another encrypted home, use PIV signing authority, or persist into a trusted boot path.
- A first-boot, firmware-inspection, or provisioning flaw with realistic inputs grants code execution at its broad raw-hardware privilege or irreversibly installs attacker-controlled keys.

High impact is often limited to one device or requires physical access, but it defeats a primary security promise or produces durable privileged compromise.

### Medium

- A sandbox or writable-state flaw requires an already authenticated local account but enables meaningful persistence, access beyond that account, or weakening of a later authentication step without immediately defeating Secure Boot or disk encryption.
- A boot-health or recovery bug causes reliable device lockout or corrupts one update slot but leaves a documented offline recovery path and does not expose plaintext or keys.
- Attestation or CHIPSEC output can be misinterpreted as stronger evidence than it is, leading an operator to trust a Path B or OEM-firmware system, while no direct verification bypass is demonstrated.
- Sensitive but non-key metadata, PCR/event-log information, or operational details leak across a local boundary and materially aid a follow-on attack.

### Low

- A hardening directive is absent from a service that already requires root-equivalent control to exploit, with no additional secret exposure, persistence, or boundary crossing.
- A documentation, CI-message, or warning bug inaccurately describes a non-production control but does not alter artifacts, enrollment, or operator security decisions in a realistic path.
- A denial of service is temporary, local, and resolved by an ordinary reboot or re-run without weakening authentication or risking data loss.
- A cryptographic-agility or hybrid-PQ assertion regresses in a way that does not downgrade classical authentication or confidentiality under the current threat model.
